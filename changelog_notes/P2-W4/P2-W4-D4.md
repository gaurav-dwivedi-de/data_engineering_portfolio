### Changelog

#### 1. Prepare the Kubernetes manifests for GHCR images

The Kubernetes application manifests were changed from the previous local image:

```yaml
image: airflow-custom:latest
imagePullPolicy: Never
```

to GHCR-based immutable image placeholders such as:

```yaml
image: ghcr.io/gaurav-dwivedi-de/data_engineering_portfolio:IMAGE_TAG
imagePullPolicy: IfNotPresent
```

The Airflow initialization Job uses a separate placeholder:

```yaml
image: ghcr.io/gaurav-dwivedi-de/data_engineering_portfolio:INIT_IMAGE_TAG
imagePullPolicy: IfNotPresent
```

The `IMAGE_TAG` value is replaced by the GitHub commit SHA during deployment.

This allows Oracle K3s to use the exact Docker image produced by the GitHub Actions run instead of the old local-only `airflow-custom:latest` image.

#### 2. Keep application credentials in the existing Kubernetes Secret

The deployment continues to use the existing Oracle Kubernetes Secret:

The CI/CD workflow checks that the Secret exists before deploying:

```bash
sudo k3s kubectl get secret weather-env >/dev/null
```

#### 5. Deploy PostgreSQL before the application workloads

The automated deployment sequence was deliberately arranged as:

```text
PostgreSQL
    ↓
MinIO
    ↓
Airflow initialization
    ↓
Airflow
    ↓
FastAPI
    ↓
Dashboard
```

The CI/CD deployment applies the PostgreSQL PVC, StatefulSet and Service first:

```bash
sudo k3s kubectl apply \
  -f $REPO/k8/postgres/pvc.yaml

sudo k3s kubectl apply \
  -f $REPO/k8/postgres/statefulset.yaml

sudo k3s kubectl apply \
  -f $REPO/k8/postgres/service.yaml

sudo k3s kubectl rollout status \
  statefulset/postgres \
  --timeout=180s
```

The rollout must complete before the deployment continues.

#### 6. Upgrade PostgreSQL to 18.6

The PostgreSQL image was changed from the previous PostgreSQL 16 image to:

```yaml
image: postgres:18.6
```

The first PostgreSQL 18 deployment exposed a data-directory layout issue because PostgreSQL 18 uses a versioned data directory.

The persistent volume mount was changed to:

```yaml
volumeMounts:
  - name: postgres-data
    mountPath: /var/lib/postgresql
```

The existing `postgres-data` PVC had already been deleted as part of the clean rebuild, so no PostgreSQL data migration was required.

After recreating the PostgreSQL pod, the logs showed that the PostgreSQL 18 cluster initialized successfully and the database became ready to accept connections.

#### 8. Recreate and run the Airflow initialization Job

The deployment workflow deliberately deletes the previous initialization Job:

```bash
sudo k3s kubectl delete job airflow-init \
  --ignore-not-found=true
```

The current immutable image is then inserted into the Job manifest:

```bash
sed "s|INIT_IMAGE_TAG|${IMAGE_TAG}|g" \
  $REPO/k8/airflow/airflow-init.yaml \
  | sudo k3s kubectl apply -f -
```

The workflow waits for successful completion:

```bash
sudo k3s kubectl wait \
  --for=condition=complete \
  job/airflow-init \
  --timeout=300s
```

The Job waits for PostgreSQL, runs the Airflow database migration and creates the Airflow administrator if required.

Deleting and recreating this Job does not delete the PostgreSQL or MinIO persistent volumes.

#### 12. Synchronize the Oracle repository automatically

The deployment job connects to the Oracle VM and synchronizes the repository before applying Kubernetes manifests:

```bash
cd $REPO

git fetch origin main
git reset --hard origin/main

git log -1 --oneline
```

This means the Oracle deployment uses the same Git repository state that was pushed to GitHub.

The deployment process therefore does not require manually editing Kubernetes manifests on the Oracle VM.

#### 13. Pass the Git commit SHA into the Oracle deployment

The GitHub Actions deployment job defines:

```yaml
env:
  ORACLE_HOST: ${{ secrets.ORACLE_HOST }}
  ORACLE_USER: ${{ secrets.ORACLE_USER }}
  ORACLE_SSH_KEY: ${{ secrets.ORACLE_SSH_KEY }}
  IMAGE_TAG: ${{ github.sha }}
```

The value of:

```text
${{ github.sha }}
```

is passed into the Oracle deployment.

The Kubernetes manifests are then rendered with that exact image tag using `sed`.

This creates the deployment relationship:

```text
Git commit SHA
      ↓
Docker image SHA tag
      ↓
GHCR
      ↓
Kubernetes deployment image
```

### Problems Faced / Decisions

#### PostgreSQL 18 data-directory change

The initial PostgreSQL 18 deployment did not start correctly because the persistent volume mount was still based on the previous PostgreSQL layout.

The mount was changed from the old data-directory target to:

```text
/var/lib/postgresql
```

The old PostgreSQL data was intentionally discarded because this was a clean rebuild.

After recreating the PostgreSQL pod, PostgreSQL 18.6 initialized correctly.

#### Old image versus GHCR image

The Oracle cluster originally used:

```text
airflow-custom:latest
```

That image was locally imported into K3s and was not suitable for the automated GitHub-to-Oracle deployment model.

D4 replaced this with:

```text
ghcr.io/gaurav-dwivedi-de/data_engineering_portfolio:<git-sha>
```

This provides an immutable relationship between source code and deployed image.

#### Airflow initialization Job

`airflow-init` is a Kubernetes Job rather than a long-running Deployment.

The deployment process therefore deletes and recreates this Job for each deployable image version:

```bash
sudo k3s kubectl delete job airflow-init \
  --ignore-not-found=true
```

The PostgreSQL and MinIO PVCs are not deleted as part of normal CI/CD deployment.

#### Clean database and MinIO rebuild

Existing PostgreSQL and MinIO data was intentionally discarded for this migration.

This was a one-time clean rebuild decision. Normal CI/CD runs do not delete these PVCs.

#### Generated project artifacts

The W7/W8/W9 pipeline generates files such as:

```text
.parquet
.csv
.png
.pkl
```

These files do not represent changes to the application container itself.

The CI/CD change-detection logic is being refined so that generated artifacts do not unnecessarily cause a Docker image build or Oracle deployment.
