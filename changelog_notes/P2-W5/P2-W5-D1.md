# P2-W5 --- Daily Development Notes

## 14/09/2026

### Task

- P2-W5 D1: Configure a Cloudflare public hostname and verify external Dashboard access.
- Expose the Weather Intelligence Platform Dashboard running on the Oracle Cloud K3s cluster through a public HTTPS endpoint.
- Establish the external access path without exposing the internal Kubernetes service or pod IP directly.
- Use Cloudflare Worker + Cloudflare Quick Tunnel + `cloudflared` to provide the public entry point.
- Route public traffic to the K3s Traefik entry point and verify that the Dashboard is reachable externally.
- Record the exact commands, infrastructure state, public response and end-to-end routing evidence.

### Why this task was required

Before P2-W5, the Weather Intelligence Platform was deployed successfully on Oracle Cloud K3s, but the application was primarily accessed through the private cluster/network path.

P2-W5 moves the platform from a private deployment into a publicly accessible application. D1 establishes the first external access layer.

The objective was not to expose the Dashboard pod directly. Instead, public traffic needed to enter through a controlled external endpoint and then reach the Kubernetes ingress layer.

The resulting access path was:

```text
Browser
    ↓
https://ml.weather-intelligence.workers.dev/
    ↓
Cloudflare Worker
    ↓
Cloudflare Quick Tunnel
    ↓
cloudflared
    ↓
K3s Traefik
    ↓
Kubernetes Ingress
    ↓
prediction-dashboard-service:8051
    ↓
Prediction Dashboard Pod
```

This design keeps the Kubernetes application behind the cluster routing layer while providing a public HTTPS hostname.

### Changelog

#### 1. Establish the public hostname

The public application hostname was configured as:

```text
https://ml.weather-intelligence.workers.dev/
```

The hostname provides the stable public-facing URL used to access the Weather Intelligence Platform.

The Cloudflare Worker forwards the incoming request to the active Cloudflare Quick Tunnel.

The Worker logic used for the public hostname was:

```javascript
export default {
  async fetch(request) {
    const incoming = new URL(request.url);

    const target = new URL(
      "https://evident-joshua-outlet-packing.trycloudflare.com"
    );

    target.pathname = incoming.pathname;
    target.search = incoming.search;

    return fetch(new Request(target, request));
  },
};
```

The Worker therefore preserves the incoming path and query string while forwarding the request to the Quick Tunnel.

The active Quick Tunnel endpoint was:

```text
https://evident-joshua-outlet-packing.trycloudflare.com
```

#### 2. Configure the Cloudflare Quick Tunnel

The Quick Tunnel was used to connect the public Cloudflare endpoint to the Traefik service inside the K3s environment.

The tunnel was started on the Oracle Cloud VM with:

```bash
nohup cloudflared tunnel --url http://10.43.178.201 > ~/cloudflared.log 2>&1 &
```

The `10.43.178.201` address is the Kubernetes Traefik LoadBalancer service address.

Using `nohup` allowed the `cloudflared` process to continue after the SSH terminal was closed.

The running process was verified with:

```bash
ps -ef | grep cloudflared | grep -v grep
```

The output showed:

```text
ubuntu   1214919       1  0 Sep17 ?        00:04:34 cloudflared tunnel --url http://10.43.178.201
```

This confirmed that the tunnel process was running and forwarding traffic to the K3s Traefik service.

The process was running independently of the interactive SSH session because its parent process was PID 1.

#### 3. Verify the Cloudflare tunnel logs

The tunnel log was checked with:


The log showed requests reaching the configured origin:
